## Bloqueos de producción y paso del propietario

1. Configurar en **Cloudflare Zero Trust → Tunnels** un Named Tunnel remotamente administrado y un public hostname de un dominio propio bajo control del propietario. Su servicio debe dirigir tráfico a `http://127.0.0.1:3100` en la máquina CAP. Guardar únicamente en `.env` `PUBLIC_WEBHOOK_URL=https://<hostname-real>` **sin ruta** y `CLOUDFLARE_TUNNEL_TOKEN=<token-privado>`. No compartir token por chat ni versionarlo. No usar `localhost` como target público de MessageSync; localhost solo es **origen interno del túnel**. Alternativa local administrada: `CLOUDFLARE_TUNNEL_NAME` con credenciales/config Cloudflare instaladas.
2. Cuando exista hostname, detener solamente la instancia CAP anterior desde la terminal que la inició y ejecutar `npm run dev:full`. Este comando prueba URL pública antes de rotar exclusivamente la suscripción CAP. Ejecutar después `npm run doctor`/`doctor:json`: exigir destino exacto y ninguna suscripción externa que produzca doble respuesta.
3. Realizar **una** ronda real según `docs/TEST_PLAN.md`; no declarar PASS de inbound/outbound, media ni prevención de duplicados reales hasta comprobar WhatsApp y ejecuciones n8n. El archivo v2 de n8n **no** fue importado; si se decide actualizar prompt, importar manualmente y verificar antes de cambiar `N8N_AI_WEBHOOK_URL`.
4. Reconciliar `UNKNOWN` contra MessageSync antes de reintentar; falta API idempotente/documentación de callback para `DELIVERED/READ`. Alta disponibilidad, PostgreSQL/Redis/object storage, multi-tenant, alarmas externas, campañas con opt-in/plantillas/límites provider y prueba con sockets simultáneos siguen siendo bloqueos de producción.
